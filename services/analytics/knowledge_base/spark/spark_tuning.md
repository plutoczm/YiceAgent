# Spark 性能调优

## 1. 核心概念

Spark 性能调优 在数据开发中经常不是一个孤立功能，而是影响建模、任务调度、资源使用和故障恢复的基础能力。理解它时要同时看数据规模、查询模式、写入方式和团队运维成本。对于 DataPilot-AI 的知识库来说，这类知识适合沉淀成可检索的工程经验：既能回答概念题，也能指导 SQL 生成、SQL Review 和数仓设计。

关键术语包括：Executor、Driver、并行度、内存管理、GC、序列化、资源队列。面试中不要只背定义，要能说明为什么需要它、适合什么场景、滥用会带来什么问题，以及线上如何观测和治理。

## 2. 工作机制

- **输入层面**：先确认数据来源、数据量、字段基数、时间分区和更新频率。
- **计算层面**：关注任务是否触发重分布、排序、状态保存、网络传输或磁盘合并。
- **存储层面**：关注文件组织、索引结构、压缩格式、分区生命周期和元数据压力。
- **治理层面**：关注口径一致性、失败重跑、数据质量、监控告警和成本边界。

在实际项目中，很多性能问题并不是参数没有调好，而是模型、分区、Join 顺序或数据写入方式从一开始就不匹配业务访问模式。优秀的数据开发会先把访问路径设计清楚，再选择执行引擎和调优参数。

## 3. 代码示例

```python
from pyspark.sql import functions as F

orders = spark.table('dwd_order_detail').where("dt >= '2026-06-01'")
users = spark.table('dim_user').select('user_id', 'city')
result = orders.join(F.broadcast(users), 'user_id').groupBy('city').agg(F.sum('pay_amount').alias('gmv'))
result.write.mode('overwrite').insertInto('ads_city_gmv')
```

这个示例体现了一个基本原则：让过滤、裁剪和聚合尽量靠近数据源，减少后续阶段的数据量。生产环境还需要配合调度参数、资源队列、失败重试和质量校验。

## 4. 性能优化经验

- 先看执行计划和 Spark UI，再调参数，避免盲目加资源。
- 宽依赖阶段重点关注 shuffle read/write、spill、GC 和 task 倾斜。
- 小表优先广播，大表优先分区裁剪、列裁剪和谓词下推。
- Executor 配置要平衡 CPU、内存、并发 task 和序列化开销。


进一步排查时，建议按顺序查看：执行计划、输入输出数据量、任务并发度、长尾任务、失败重试、磁盘和网络 IO、内存与 GC、元数据访问。如果一个优化只能在单次任务上生效，却破坏了长期可维护性，通常不值得采用。

## 5. 常见坑

- 只看单条 SQL，不看上游数据分布和下游复用方式。
- 为了短期提速增加过多特殊逻辑，导致任务不可重跑或不可解释。
- 忽略小文件、热点 Key、长事务、状态膨胀等慢性问题。
- 没有把优化经验固化到规范、模板和 Review 规则中。

## 6. 面试高频问题

### 问题：Spark 为什么会产生 Shuffle？

答案：当算子需要跨分区重新分布数据时会产生 Shuffle，例如 groupByKey、reduceByKey、join、distinct 和 repartition。

扩展：可以继续追问线上如何验证、出现异常时如何定位、与其他方案相比有什么取舍。

### 问题：AQE 解决什么问题？

答案：AQE 在运行时根据真实统计信息调整 Join 策略、合并小分区，并尝试优化倾斜分区。

## 7. 项目表达建议

在简历或面试中，可以这样描述：围绕 Spark 性能调优 建立了统一规范，通过执行计划分析、数据分布治理和任务监控，把开发经验沉淀到知识库与自动化 Review 中，降低重复排查成本，并提升 SQL 和数仓设计质量。

## 8. 实战检查清单

- 上线前确认数据量级、字段基数、分区范围、任务并发和资源队列是否匹配。
- 每次优化都要保留对比指标，包括扫描行数、输入输出字节、任务耗时、失败次数和资源消耗。
- 对核心任务建立监控：延迟、产出分区、空值率、重复率、异常波动和下游依赖状态。
- 重要规则应沉淀为开发规范和 Review 清单，避免只靠个人经验临时处理。
- 当业务口径变化时，要同步更新模型说明、指标定义、调度依赖和知识库文档。
