# V2-2 本地业务演示

当前阶段完成业务闭环与最小控制台。全部价格、商品、规则、支付/退款结果是模拟数据；没有真实外部平台、实际支付或到账。

## 启动与停止

从 `D:\Projects\WorkflowOps` 执行：

```powershell
& ".\.runtime\v2\envs\main\Scripts\python.exe" -B scripts/manage.py up
```

浏览器打开 `http://127.0.0.1:8020`。首次选择“客户 A1”并点击“选择身份”。当前服务已经启动时直接打开页面即可；重复启动会按进程归属安全门禁拒绝，不另起一份服务。

停止 HTTP：

```powershell
& ".\.runtime\v2\envs\main\Scripts\python.exe" -B scripts/manage.py down
```

数据库、向量资源、模型及演示结果保留。启动不自动迁移或重置。初始业务 schema/seed 已准备。

## 客户和运营

六个固定演示身份覆盖两个租户：客户 A1/A2、运营 A、客户 B1/B2、运营 B。服务器由固定身份决定租户与权限；请求不能自行指定租户、价格或权限。普通客户只看到自己的订单和工单，运营只看到所属租户。

演示身份可切换，用于验证权限边界；这是本机演示机制，不是生产账户认证。

## 一次低额完整流程

1. 选择客户 A1，在商品区选择电商充电线或外卖奶茶，生成下单草案；在动作区核对商品数量和总额，点击确认，才产生订单。
2. 在该订单生成支付草案，客户确认后状态为模拟支付申请中。
3. 切换运营 A，在订单卡片执行支付成功模拟事件。支付金额由服务端确定。
4. 逐次执行履约推进：电商依次待发货→已发货→已送达；外卖依次已接单→制作中→配送中→已送达。
5. 切回客户 A1，生成整单退款草案并确认。此时是退款申请，退款金额还未到账。
6. 切换运营 A，执行退款成功模拟事件，页面显示结构化的实际模拟已退金额。

普通整单退款不自动取消履约。支付、配送、退款是三个独立事实。

## 高额取消与审批

电商演示手机 899 元、外卖家庭套餐 129 元，适合演示审批。

1. 下单、客户确认支付草案、运营模拟支付成功。
2. 在取消边界内，客户生成取消草案。草案先进入待审批，订单尚未取消。
3. 运营 A 审批通过；此时依然没有提交取消或退款。
4. 客户 A1 再次核对并确认。一个事务提交订单取消及整单退款申请。
5. 运营模拟退款成功或失败；失败可经新的草案/确认重新申请。

电商只允许发货前取消，外卖只允许商家接单前取消。电商退款/已支付取消金额严格超过 500 元、外卖严格超过 100 元才需要运营审批；等于阈值不触发审批。

草案 15 分钟过期；订单、规则或商品版本改变后旧报价失效。失效需要新草案与确认，不能利用旧审批绕过校验。

## 异常工单与拒绝案例

在订单卡片“异常工单”或工单表单填写问题，生成草案并客户确认。运营分派、回复、调整状态分别生成草案并确认；客户可点击“查看对话”读取已持久化消息。

可以选择已发货电商订单或已接单外卖订单申请取消，观察业务拒绝，再创建异常工单。切换客户 A2 或 B1 时，A1 的订单和工单不会泄露。

超时或提交结果未知会显示 `unknown_outcome` 并锁定新写入。使用页面只读核对按钮按当前请求 ID 查询，或通过动作 ID 查询，不自动重放。错误和并发场景的完整验证见 [V2_2_VALIDATION](validation/business.md)。

## 固定剧本

```powershell
& ".\.runtime\v2\envs\main\Scripts\python.exe" -B scripts/manage.py replay-demo --approved
```

这会在 v2 专用库中创建 4 个新演示订单并完成两类送达退款、高额取消退款，结果保留。重复执行重新创建一轮，不清空过去数据。24 个固定 seed 订单也覆盖两租户、他客户、各履约状态与高低金额，适合只读检查。

Agent 对话、三模型/RAG、上下文与记忆展示属于后续阶段，当前页面没有这些能力。第二阶段未进行账号登录、模型调用或计费。
