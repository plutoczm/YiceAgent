# WorkflowOps v2 Spec

版本：2.0
日期：2026-10-02
状态：用户已确认的需求基线；实际实施进度与证据见 [PLAN.md](PLAN.md)。

## 1. 产品目标与范围

构建一个用于本机学习和面试演示的业务知识与问题处理 Agent，以电商和外卖订单为场景，重点展示：

- 真实模型驱动的意图识别、知识回答和工具选择。
- 短期记忆、长期记忆、会话摘要与上下文预算。
- 什么时候裁剪、裁剪什么、如何保留用户纠正和关键事实。
- 真实向量检索、模型重排、引用与无证据拒答。
- 工具循环控制，以及业务操作的确认和审批边界。

电商和外卖均覆盖政策问答、订单查询、下单、模拟支付、配送推进、取消、整单退款和异常工单。业务状态真实写入本地数据库，订单和规则属于模拟数据。

采用手动推进和可重放剧本。首版不增加自动配送调度、真实平台接口、真实支付、部分退款、库存、优惠券、物理退货物流或公网账号系统。

运行时不联网搜索业务资料。联网仅用于开发阶段搜集资料并构建版本化知识库。

原分析报表源码通过 v1.0.0 Git 历史保留，但快照、SQL 报表和 Text2SQL 退出 v2 必做范围。Jev 为可选实验，不阻塞核心完成。

## 2. 架构与模型接入

### 2.1 一个主要应用与隔离工作进程

采用 Python 模块化主应用，统一提供 Web UI、Agent、上下文管理、记忆、业务状态机和工具执行。

```text
浏览器工作台
     │
Python 主应用
     ├─ LangGraph 受限 Agent Loop
     ├─ Context Manager 与 Memory Manager
     ├─ 电商／外卖业务状态机
     ├─ 工具校验、确认、审批与运行记录
     │
     ├─ Pi Node 桥接 ── ChatGPT OAuth
     ├─ DeepSeek HTTP API
     ├─ Ollama HTTP API ── qwen3:8b
     └─ BGE 推理工作进程
              │
        PostgreSQL ＋ Qdrant
```

- 新建主应用和推理专用环境，不把三套旧环境直接合并；旧环境继续保留。
- 主应用使用独立包名，避免原服务都叫 app 的导入冲突。
- 复用原工具契约、运行上限、业务确认、审批、幂等和权限设计；提取代码必须保留来源与相应测试。
- BGE 工作进程和 Pi 桥接采用带请求 ID 的 JSONL 标准输入输出协议，支持超时、取消、健康检查和明确错误。
- 按用户后续确认，BGE 默认采用 auto：GPU 可用且显存满足预算时优先 cuda:0；否则明确回退 CPU。BGE 与 Qwen 的本地任务按显存预算串行调度，不停止其他程序或卸载非本项目管理的模型来抢占显存。
- PostgreSQL 和 Qdrant 使用 v2 专用数据库或资源，禁止迁移时重置 v1 数据。
- 主应用只监听本机回环地址。停止应用不删除数据库、向量索引或模型。

### 2.2 三条必过模型通道

| 通道 | 接入与用途 | 完成要求 |
|---|---|---|
| ChatGPT | 复用 Pi 的 Codex OAuth 与模型适配；浏览器完成账号授权 | 真实验证意图、RAG、工具调用、压缩与会话切换 |
| DeepSeek | API Key；默认使用官方当前 deepseek-flash 的非思考模式 | 同上 |
| Qwen | 现有 Ollama qwen3:8b，默认关闭 thinking，配置上下文窗口 | 同上；允许耗时高于云模型 |

Pi 只负责认证和模型协议，不接管本项目的 Agent Loop、记忆、工具执行或压缩策略。Pi 有独立的 [ChatGPT OAuth 实现](https://github.com/earendil-works/pi/blob/main/packages/ai/src/auth/oauth/openai-codex.ts)；DeepSeek 模式参数按其 [官方文档](https://api-docs.deepseek.com/guides/thinking_mode/)适配。

首次设置时，从账号实际可用的模型列表选定 ChatGPT 模型并保存 ID；每次验收记录实际模型 ID、配置与时间。不得使用未经验证的模型名称冒充已接入。

统一接口包含消息、工具定义、结构化输出要求、输出预算、截止时间，以及标准化响应、工具调用、usage 和错误。供应商差异留在适配器内。

- 同一会话可以切换模型；切换发生在完整 turn 边界。
- 切换后依据新模型能力重新组装上下文，不能直接转发另一供应商的原始响应对象。
- 必需的供应商协议字段由适配器维护，不显示为上下文调试内容。
- 登录失效、额度不足和模型不可用均显式失败，不偷偷切换模型。
- OAuth 凭据保存在项目专用、Git 忽略的位置，不读取其他工具的既有登录凭据。

首轮 DeepSeek 与 Jev 计费调用合计预算不超过 100 元。调用前按已配置费率预留最高成本，结束后按 usage 更新；未知 usage 按预留值计账。没有可靠费率配置时禁止自动计费测试。ChatGPT 订阅额度单列，不能伪造人民币费用。

## 3. Agent、RAG 与上下文管理

### 3.1 真实 RAG

检索链路固定为：

```text
文档解析与结构切分
→ BGE-M3 embedding
→ Qdrant 入库
→ BM25＋Dense 召回
→ RRF 合并候选
→ BGE Reranker 重排
→ 证据预算与答复门槛
→ LLM 带引用回答
```

- Embedding 使用 BAAI/bge-m3；Reranker 使用 BAAI/bge-reranker-v2-m3，执行真实模型推理。[Embedding](https://huggingface.co/BAAI/bge-m3)、[Reranker](https://bge-model.com/bge/bge_reranker_v2.html)
- 初始切分目标为约 400 token，重叠约 60 token，优先保留标题、段落和表格行结构。
- BM25 与 Dense 各召回 20 项；合并去重后最多重排 20 项，最终最多提供 5 个完整证据块。
- 证据超预算时减少块数量，不截断金额、条件、表格行或来源关系。
- 保存文档 ID、版本、来源、许可记录、原文哈希、chunk ID、embedding 模型和索引版本。
- 模型或切分策略改变时建立新索引，验证后切换；不能混查不同 embedding 空间。
- 知识与长期记忆使用独立 collection，所有查询由服务端注入访问过滤。[Qdrant 过滤设计](https://qdrant.tech/documentation/manage-data/multitenancy/)

业务资料采用开源参考和自编中文演示手册。电商可参考 Medusa，外卖可参考 nextorders/food；纳入的具体文件需记录提交版本、许可和署名。[Medusa 许可](https://github.com/medusajs/medusa/blob/develop/LICENSE)、[外卖项目许可](https://github.com/nextorders/food/blob/main/LICENSE)

平台公开资料仅作带来源的参考。自建支付、取消和退款规则统一标为“演示规则”，不可称为淘宝或外卖平台官方规则。

### 3.2 意图识别与工具循环

意图为封闭集合：知识咨询、订单查询、下单、支付、取消、退款、工单、记忆管理和澄清。

分类输出经 Pydantic 校验；模型自报置信度只作辅助，不作为业务授权。缺少订单、商品或操作范围时先澄清。

白名单工具支持检索知识、读取记忆、查商品、查订单、查工单，以及生成业务动作草案。模型不得调用任意 SQL、URL、Shell 或直接修改数据库。

每个 turn 默认：

- 最多 6 次模型调用、8 次工具调用。
- 单次参数修复最多 1 次，计入总预算。
- 总截止时间 10 分钟，用户可以取消。
- 相同工具、规范化参数和业务版本连续重复 2 次，停止执行。
- 连续 3 次工具结果没有新增信息，或重复出现同一工具调用环，停止并解释原因。

读取相同对象的新版本不视为无意义重复。业务幂等由业务层保证，不能只按模型生成的 tool-call ID 去重。

### 3.3 三类记忆

| 类型 | 保存与使用规则 |
|---|---|
| 短期记忆 | 持久化当前会话原始消息；请求模型时按预算选择，不无限拼接 |
| 会话摘要 | 保存目标、约束、用户纠正、已确认信息、未解决问题及原消息引用；带版本 |
| 长期记忆 | 自动提取候选，用户确认后保存；支持查看、修改、删除与过期 |

长期记忆以 PostgreSQL 为权威存储，Qdrant 为召回索引。即使向量删除失败，查询后也必须根据权威状态过滤已删除记录。

- 候选保存来源消息、类型、归属和提取模型。
- 用户纠正使旧候选失效；已确认记忆被修改时保留版本关系。
- 首版保存偏好和用户明确确认的稳定信息。
- 不保存凭据，不自动保存模型推测，不把对话里的订单状态作为长期业务事实。
- 订单和支付事实必须重新查询业务模块。
- 摘要、长期记忆和文档都作为数据，不能提升为系统指令。

### 3.4 上下文预算与压缩

默认应用总窗口为 8192 token；输出预留 1536、安全余量 512，可用输入预算为 6144。这是应用预算，不宣称供应商原生窗口只有 8192。

每次模型调用前检查预算，包括工具返回后的下一次调用。达到输入预算的 75% 时整理到约 55%；提供手动压缩按钮和 4096/8192/16384 三档预算，不能超过模型声明的上限。

裁剪顺序：

1. 去除重复、过期和低相关的工具结果、记忆与检索证据。
2. 大结果改为引用或分页，保存可重新读取的原始结果。
3. 较早的完整对话轮次生成结构化摘要，优先保留最近 4 个完整轮次。
4. 固定保留当前请求、最新纠正、未完成任务、操作引用和确认状态。
5. 仍超预算时缩小任务范围或请求用户拆分输入；不得静默丢弃关键约束。

工具调用与结果必须成组处理。摘要保存消息引用，并核对必须保留的 ID、数字和明确约束；校验失败时不提交摘要，改用可容纳的原始引用或明确报告容量不足。

压缩请求本身也经过预算检查。原始历史不因上下文裁剪而删除。重复压缩使用同一历史范围和版本标识，防止重复叠加。

Token 面板注明精确计数或估算来源；不能把字符数直接标成精确 token 数。供应商报告的实际 usage 用于校准估算。

### 3.5 幻觉与安全处理

- 政策回答必须引用本轮可访问的证据；无证据、来源冲突或过期时明确说明。
- 引用 ID、出处和版本做确定性校验。
- 金额、支付和审批结果来自结构化业务返回，由界面按真实字段展示。
- 回答涉及不能被证据支持的结论时，停止发布该结论，返回澄清或转人工。
- 模型评审和可选 Jev 判断只作辅助，不能证明事实一定正确。
- 用户、文档、工具结果和记忆均不能改写权限、执行预算或审批规则。

Jev 可用于意图分类、记忆候选筛选或相关性判断，单独记录实际效果；未运行时显示 NOT_RUN。[Jev 官方能力](https://docs.typesafe.ai/introduction)

## 4. 业务闭环、界面与接口

### 4.1 模拟业务规则

采用两种独立订单类型与显式状态机：

| 类型 | 正常状态路径 | 取消边界 |
|---|---|---|
| 电商 | 待支付 → 已支付 → 待发货 → 已发货 → 已送达 | 发货前可取消 |
| 外卖 | 待支付 → 已支付 → 已接单 → 制作中 → 配送中 → 已送达 | 商家接单前可取消 |

支付、退款分别保存状态，不混入配送状态。支付成功、失败、退款成功和失败由模拟控制台或剧本事件推进。

- 商品价格、总额、客户归属和商家归属由服务端计算，金额使用精确 decimal 类型。
- 下单、支付、取消、退款和工单写入均先生成封闭动作草案，由用户确认。
- 已支付取消按一个关联动作处理取消与整单退款申请；确认和必要审批通过前不改变订单终态。
- 整单退款不得超过实际支付金额；拒绝重复提交、未支付订单和失效业务版本。
- 演示高金额审批阈值：电商超过 500 元，外卖超过 100 元；由运营审批，再由客户确认。
- 商家、配送及支付推进由运营模拟控制台执行，Agent 无权代替运营推进。
- 草案 15 分钟过期；订单版本或规则版本改变时失效并重新报价。
- 写入结果未知时返回 unknown_outcome，通过动作 ID 查询核对，禁止自动重放。
- 不符合取消或退款规则的请求可提出异常工单，创建仍需确认。

固定 seed 生成两类订单和商品目录；至少两个演示租户，覆盖他客户、他租户、各生命周期状态和高低金额案例。演示时不伪造真实订单或到账记录。

### 4.2 工作台

沿用 FastAPI 同源 HTML/CSS/JavaScript，新增五个主要视图：

1. **Agent 对话**：流式状态、引用、工具结果、动作确认、模型切换。
2. **订单与模拟控制台**：商品、下单、支付、配送、取消、退款、审批和工单。
3. **上下文面板**：预算分配、入选与省略内容、理由、摘要版本、压缩前后大小。
4. **记忆与知识库**：候选确认、记忆管理、资料导入、来源、版本和索引状态。
5. **运行记录**：步骤、工具参数校验、循环停止、错误、usage 和模型通道。

不展示模型内部思维链。原始会话和证据只在所属用户的调试视图中读取；普通日志只记录元数据。临时流式内容与已验证最终回答要有明确区分。

### 4.3 最小接口契约

| 接口组 | 内容 |
|---|---|
| /api/v2/conversations | 创建、读取会话及消息；提交带客户端请求 ID 的 turn |
| /api/v2/runs | 查询运行、流式事件、取消、读取上下文快照及裁剪记录 |
| /api/v2/models | 可用通道、能力、登录状态与配置；不返回凭据 |
| /api/v2/knowledge | 导入、资料和索引状态、来源信息 |
| /api/v2/memories | 候选、确认、修改、删除；归属由服务端确定 |
| /api/v2/orders | 创建草案与订单查询 |
| /api/v2/actions | 确认、取消、审批、查询结果 |
| /api/v2/simulator | 受控支付、商家和配送事件，执行固定剧本 |
| /api/v2/tickets | 查询、创建草案、回复及运营处理 |

主要类型包括 Conversation、TurnRequest、RunRecord、ContextSnapshot、ConversationSummary、MemoryCandidate、MemoryRecord、EvidenceChunk、Order、ActionDraft 和 SimulationEvent。

输入不接受裸租户、权限、数据库路径或任意工具目标。同一会话只允许一个活动 turn；重复客户端请求 ID 返回已有运行，不再次触发模型和业务操作。

等待用户确认时结束当前 run，业务动作持久化；后续确认开启关联 run，不依赖把整个 LangGraph 暂停在内存中。

## 5. 实施顺序与完成标准

### 5.1 实施顺序

1. **基础重组与协议**：建立新应用、隔离环境、数据库、模型接口和启动入口，保护 v1 数据与未知修改。
2. **双场景模拟业务**：完成两类状态机、动作草案、确认、审批、幂等、控制台和固定剧本。
3. **三模型与真实 RAG**：完成 Pi OAuth、DeepSeek、Qwen、BGE、Qdrant、重排与来源管理。
4. **上下文与记忆**：完成预算、压缩、记忆候选确认、跨模型重组及工具循环控制。
5. **交互展示与验收**：完成面板、真实调用证据、故障场景和演示说明；Jev 单列可选实验。

每阶段运行相关 lint、已配置的类型检查、单元和集成测试，审阅 diff 后再更新证据。安装、模型下载、登录、迁移和计费调用在实施阶段按项目约定取得授权。本 Spec 不授权删除、覆盖用户级配置、提交或推送。

### 5.2 必须通过的验收

- 两类订单分别完成下单、支付、配送、取消、整单退款和异常工单剧本；非法状态、越权和重复操作产生零非法写入。
- 真实 embedding 入库，Qdrant 重启后可检索，真实 Reranker 完成推理；无哈希向量或规则排序冒充模型。
- 三条模型通道均完成真实政策回答、意图澄清、工具查询、业务草案和长对话场景；任一不可用时不得标记整体完成。
- 每通道至少一个 30 轮会话，加入早期约束、用户纠正、无关消息和工具结果，实际触发压缩；检查指定关键事实与纠正没有丢失。
- 同一会话切换三个模型，当前任务、摘要、确认状态和已确认记忆保持一致，预算重新计算。
- 长期记忆确认后跨会话召回；修改后旧值不再生效，删除后即使索引暂未删除也不能召回。
- 缺证据、冲突证据、恶意文档、伪造引用和虚构订单事实均有明确处理结果。
- 重复调用、调用环、超大工具结果、窗口不足、超时和取消均能终止并保留可核对状态。
- 页面能展示实际上下文组成和压缩原因；浏览器实际执行核心场景，不能用静态截图代替。
- 计费预算门禁通过；所有真实调用记录通道、模型、usage 可知性和错误，未执行项与 skip 单列。

知识库建立至少 40 条冻结查询样本，覆盖语义改写、两类业务、无答案和冲突资料；真实检索 HitRate@5 目标不低于 85%。该数字是验收目标，尚无实际结果。

真实模型验收采用固定输入和结果判据，允许各通道回答措辞和耗时不同。安全不变量必须全部通过；失败案例保留，不以另一模型的成功替代。
